CyberSOC v2.0

Setup & operating instructions

CyberSOC is a single-page security operations console: a status map, an alert feed and command line, a dossier of subjects and organizations, a documentation repository, and an RSS log view. Data is stored in Firebase (Firestore) and access is controlled by per-account roles. Public feeds are fetched through a small Cloudflare Worker.

Overview

The app is one file, index.html (HTML, CSS and JavaScript). There is no application server any more. Three outside services do the work the old server.js did:

  • Firebase Authentication signs people in (Google or email and password).
  • Cloud Firestore stores the dossier, files, country intel, each user's RSS feed list and the role of every account. Security rules decide who can read and write.
  • A Cloudflare Worker (worker/worker.js) fetches public feeds for the browser: RSS, threat intelligence, IP geolocation and DownDetector. It is read-only and stores nothing.

Quick start

  1. Firebase: turn on the sign-in methods, create the Firestore database and publish the rules. See Firebase config.
  2. Serve the folder over http. Sign-in does not work from a file:// path. For a local test, run one of these in the project folder and open http://localhost:8080:
    macOS / Linux
    python3 -m http.server 8080
    Windows
    py -m http.server 8080
  3. Sign in once with the account that should be the first admin, then make it an admin in the Firebase console. See First admin.
  4. Deploy the Worker and paste its URL into SETTINGS → Feed proxy. See Cloudflare Worker.
  5. Import your old data if you want it. See Migrating old data.

Security rules

Paste these into Firebase console → Firestore Database → Rules and press Publish. The same text is in firestore.rules.

Firestore rules
rules_version = '2';

// CyberSOC — Firestore security rules
// Roles live in soc_roles/{uid}.role :  "admin" | "viewer" | "pending"
//   admin   read + create / update / delete in soc_dossier, soc_files, soc_sitrep
//   viewer  read only; never receives dossier documents with confidential == true
//   pending signed in, not yet approved: no access to any data collection
// Anything not matched below is denied.
service cloud.firestore {
  match /databases/{database}/documents {

    function signedIn() {
      return request.auth != null;
    }
    function rolePath() {
      return /databases/$(database)/documents/soc_roles/$(request.auth.uid);
    }
    function hasRole(r) {
      return signedIn() && exists(rolePath()) && get(rolePath()).data.role == r;
    }
    function isAdmin()  { return hasRole('admin'); }
    function isViewer() { return hasRole('viewer'); }
    function validRole(r) { return r in ['admin', 'viewer', 'pending']; }

    // ---- accounts & roles -------------------------------------------------
    match /soc_roles/{uid} {
      allow get:  if signedIn() && (request.auth.uid == uid || isAdmin());
      allow list: if isAdmin();

      // First sign-in: a user may register THEMSELVES, and only as "pending".
      allow create: if signedIn()
                    && request.auth.uid == uid
                    && request.resource.data.keys().hasOnly(['role', 'email', 'displayName', 'createdAt'])
                    && request.resource.data.role == 'pending'
                    && request.resource.data.email == request.auth.token.get('email', '');
      allow create: if isAdmin() && validRole(request.resource.data.role);

      // Admins manage other accounts. Nobody can change or delete their own
      // role document (no self-promotion, no accidental lock-out).
      allow update: if isAdmin() && request.auth.uid != uid && validRole(request.resource.data.role);
      allow delete: if isAdmin() && request.auth.uid != uid;
    }

    // ---- dossier ----------------------------------------------------------
    // Viewers can only read documents whose confidential flag is false, and
    // their queries must filter on it:  where('confidential', '==', false)
    match /soc_dossier/{id} {
      allow read:           if isAdmin() || (isViewer() && resource.data.confidential == false);
      allow create, update: if isAdmin() && request.resource.data.confidential is bool;
      allow delete:         if isAdmin();
    }

    // ---- documentation files ---------------------------------------------
    match /soc_files/{id} {
      allow read:  if isAdmin() || isViewer();
      allow write: if isAdmin();
    }

    // ---- country intel (document id = ISO-3 code) ------------------------
    match /soc_sitrep/{id} {
      allow read:  if isAdmin() || isViewer();
      allow write: if isAdmin();
    }

    // ---- each user's own RSS feed list -----------------------------------
    match /soc_feeds/{uid} {
      allow read, delete:   if signedIn() && request.auth.uid == uid;
      allow create, update: if signedIn() && request.auth.uid == uid
                            && request.resource.data.feeds is list
                            && request.resource.data.feeds.size() <= 40;
    }
  }
}

One-time console setup

  1. Authentication → Sign-in method: enable Google and Email/Password.
  2. Authentication → Settings → Authorized domains: add the domain you host the site on. localhost and the project's web.app and firebaseapp.com domains are there by default.
  3. Firestore Database → Create database in production mode, then publish the rules above.

First admin

The rules do not let anyone make themselves an admin, so the first one is set by hand:

  1. Open the site, press SIGN IN and sign in. The app creates soc_roles/<your uid> with role: "pending".
  2. In the Firebase console open Firestore Database → soc_roles, open your document and change role to admin.
  3. Back in the app the badge disappears within a second or two. From now on you manage everyone else in SETTINGS → Access control.

Optional: host on Firebase

Deploy site and rules
firebase deploy

The site is then at https://infosec-database.web.app. The Worker's allow-list already includes that address.

Roles & access

Every account that has signed in has a document in soc_roles, keyed by its user id.

RoleReadWrite
adminEverythingAdd, edit and delete dossier files, documents and country intel. Manage roles. Import legacy data.
viewerFiles, country intel, and dossier files whose Confidential switch is offNothing
pendingNothing (dummy data)Nothing
  • Granting access: a new person signs in, then an admin opens SETTINGS → Access control and changes their row from PENDING to VIEWER or ADMIN.
  • Removing access: press REMOVE on their row. If they sign in again they reappear as pending.
  • You cannot change or remove your own role. Ask another admin, or use the Firebase console.
  • Confidential switch: every dossier editor has a Confidential switch, on by default. While it is on, only admins receive that file; the rules stop it being sent to viewers at all. Turn it off to release a file to viewers. Released files show a green VIEWER-RELEASABLE stamp; confidential ones show a red square in the roster.

Data model

All collections start with soc_. Every write records updatedBy (user id), updatedByEmail and updatedAt.

CollectionDocument idContents
soc_rolesuser idrole, email, displayName, createdAt
soc_dossierprofile id (sub-…, org-…)One person or organization. Includes confidential (boolean) and the photo as an embedded, downscaled image.
soc_filesnode id (fld-…, file-…)One folder or one document (title, subtitle, tags, body, parent).
soc_sitrepISO-3 country codePosture, summary, allies, adversaries and alerts for one country.
soc_feedsuser idfeeds: that user's own RSS feeds (name and URL). Private to the user.

Firestore limits a document to 1 MiB. Photos are downscaled to 384 px and images pasted into documents to 1100 px so entries stay well under it; the app refuses to save anything over about 900 KB.

Console preferences (theme, toggles, which folders are collapsed, the proxy URL, the geocoding cache) stay in the browser's local storage on each device.

Cloudflare Worker

Browsers refuse to read most third-party feeds directly, so the Worker fetches them. It only answers GET requests from the site origins you list, has no write or shell routes, and keeps nothing.

RouteReturns
/api/healthLiveness check
/api/rss?url=An RSS or Atom feed (XML only, 2 MB cap, public hosts only, cached 2 minutes)
/api/threat-intel?cats=CISA KEV, Feodo, ThreatFox, URLhaus, Tor, ransomware.live, OpenSky. Only the categories switched on in SETTINGS are contacted.
/api/ip-intel?q=Geolocation and ASN for the whois command
/api/downdetector?q=, /api/downdetector-statusDownDetector report series (best effort; DownDetector often blocks automated requests)

Deploy

You need a free Cloudflare account and Node.js installed on your computer (only for the deploy tool).

Deploy the Worker
cd worker
npx wrangler login
npx wrangler deploy

The command prints the Worker's address, like https://cybersoc-feeds.yourname.workers.dev.

Allow your site

Edit ALLOWED_ORIGINS in worker/wrangler.toml so it lists every address the site is opened from (scheme, host and port, no trailing slash), then deploy again. Requests from any other origin get 403.

worker/wrangler.toml
# CyberSOC feed proxy — deploy with:  npx wrangler deploy
name = "cybersoc-feeds"
main = "worker.js"
compatibility_date = "2024-11-01"
workers_dev = true

[vars]
# Comma-separated list of site origins allowed to call this worker.
# Use the exact origin of wherever index.html is served (scheme + host + port,
# no trailing slash). "*" allows any site — avoid it outside of testing.
ALLOWED_ORIGINS = "https://infosec-database.web.app,https://infosec-database.firebaseapp.com,http://localhost:5000,http://localhost:8080,http://127.0.0.1:8080"

Point the app at it

Either open SETTINGS → Feed proxy, paste the address and press SAVE (stored on that device), or set it for everyone by editing this line near the top of the first large script in index.html:

index.html
const WORKER_URL = "https://cybersoc-feeds.yourname.workers.dev";

Press TEST in SETTINGS to check it. Opening the Worker address straight in a browser tab shows origin not allowed; that is expected, because a typed address sends no origin.

Without the Worker

The app still runs. RSS feeds are fetched directly, so only publishers that allow cross-site reads will load, and the others show as unreachable in the LOGS tab. Threat intelligence, IP geolocation and DownDetector stay off.

How status is read from a feed

  • Azure lists only incidents that are open now. A region turns degraded or outage when an open incident names it. Names are matched whole, longest first, so “East US 2” does not also flag “East US”. Incidents that name no region appear in the alert feed without a marker.
  • SolarWinds is an incident history. Each entry's newest update label decides its state: Investigating, Identified, Update and Monitoring count as open; Resolved, Completed and Scheduled do not.
  • Microsoft 365 and Power Platform publish a running status. Only the newest entry counts. Microsoft's standard “This site is updated when service issues…” text is treated as healthy; wording such as “investigating” or “unable to access” raises an alert. This is a wording heuristic, so check the entry itself in the LOGS tab if an alert looks wrong.
  • When a feed cannot be loaded the console says FEED OFFLINE and shows that source as unknown. It never invents a status.

Adding your own feeds

Open LOGS, type a feed address (RSS 2.0, Atom or RDF) and an optional name, and press ADD FEED. Click a feed to filter the entries to it; press × to remove one of yours.

  • Signed in: the list is saved to your account (soc_feeds/<your uid>) and follows you to other devices.
  • Not signed in: the feed works until you reload the page. It is not saved anywhere.
  • Up to 40 feeds per account. Feed text is always shown as plain text; links open in a new tab.

Migrating old data

The app no longer reads or writes local .json files. Your previous files are in legacy-data/.

  1. Sign in as an admin.
  2. Open SETTINGS → Import legacy data → CHOOSE FILE.
  3. Pick soc_dossier.json, then repeat for soc_files.json and soc_sitrep.json. The app works out which is which.
  4. Delete the legacy-data folder.

Imported dossier files are all marked confidential; release individual ones to viewers by editing them. Importing a file twice overwrites the same documents rather than duplicating them. Photos that pointed at files in assets/images/ keep working only if those image files are still hosted; re-upload them in the editor to embed them.

Security notes

  • The rules are the control. Hiding buttons in the page is a convenience. A viewer who edits the page still cannot write, and cannot read a confidential dossier file, because Firestore refuses.
  • Consider App Check (Firebase console) if you host this publicly, to limit use of the project from other sites.
  • Keep ALLOWED_ORIGINS specific. * lets any website use your Worker as a feed proxy.
  • Document bodies are sanitized when saved and again when shown: only basic formatting, http(s) links and raster images survive.
  • Anyone can create an account (that is how Google sign-in works), but a new account is pending and can read nothing until an admin approves it.
  • Do not host legacy-data/.
  • Geocoding (OpenStreetMap Nominatim), country borders (jsDelivr), map tiles (CARTO), Leaflet (unpkg), fonts (Google) and domain registration data (rdap.org) are requested by the browser directly.
